# AppArmor M2：exec 标签绑定与进程查询

本报告保留 2026-10-27 的实现和测试记录。
2026-10-28 的严格审阅发现 M1 基线的 release 注册和 securityfs 所有者问题；
当前整合工作见[审阅修复计划](../plans/2026-10-28-apparmor-m2-review-fixes.md)。
下方历史结果不代表修复后分支已完成重新验证。

本次范围是精确路径 attachment、凭据标签生命周期及只读进程查询，放在同一个 PR。
基线是完整 M1 `0c527109f239b62151fa2a0ed97eb400fa4b6920`。
这不是权限执行阶段；
`enforce` 和 `complain` 目前只表示已加载 profile 的模式。

## 可观察行为

- 初始进程保持 `unconfined`。
  加载策略不改变已经运行的进程。
- unconfined 进程成功 exec 时，以已打开的原始可执行文件路径匹配 attachment。
  脚本使用脚本路径；
  符号链接使用解析后的目标路径；
  路径相对 mount namespace 根目录。
- fork/clone 复制各自的标签槽，分享不可变 profile 引用。
  子进程 exec 不修改父进程标签。
- 已有标签的进程再次 exec 时保留该标签；
  本阶段没有 profile 切换规则。
- `/proc/<pid>/attr/current` 查询主线程；
  `/proc/<pid>/task/<tid>/attr/current` 查询指定线程。
  输出为 `unconfined\n` 或 `<profile> (<mode>)\n`。
- 跨任务查询使用现有 READ_WITH_FS_CREDS 授权。
  每次打开保存一次快照，分段读取、exec 或目标退出不会改变该文件描述符的内容。
  重新打开取得当时的状态，写入被拒绝。
- 未选中提供查询的 LSM 时，打开 `attr/current` 返回 EINVAL。

## NixOS 演示

先启动带 `lsm=apparmor,yama` 且包含 `apparmor_parser` 5.0.2 的 M2 内核。
以下示例由目标自身读取标签并通过 FIFO 报告，然后父 shell 按目标 PID 查询：

```sh
mkdir /tmp/aa-demo
cat > /tmp/aa-demo/program <<'EOF'
#!/bin/sh
IFS= read -r label < /proc/self/attr/current
printf '%s\n' "$label" > /tmp/aa-demo/ready
IFS= read -r release < /tmp/aa-demo/release
EOF
chmod +x /tmp/aa-demo/program
cat > /tmp/aa-demo/profile <<'EOF'
profile demo /tmp/aa-demo/program {
}
EOF
apparmor_parser --stdout /tmp/aa-demo/profile > /tmp/aa-demo/policy.bin
apparmor_parser --binary --add /tmp/aa-demo/policy.bin
mkfifo /tmp/aa-demo/ready /tmp/aa-demo/release
/tmp/aa-demo/program & demo_pid=$!
IFS= read -r self_label < /tmp/aa-demo/ready
printf 'self: %s\n' "$self_label"
cat /proc/$demo_pid/attr/current
echo go > /tmp/aa-demo/release
wait "$demo_pid"
```

两次查询均应显示 `demo (enforce)`。
自动化 NixOS 测试同时观察两个不同标签的目标和一个 unconfined 目标，并核对自查与外查一致。
重复演示前需要重启或换 profile 名称及路径；
M2 保持 M1 的仅追加策略接口，没有卸载/替换接口。

## 成本与实现选择

`None` 直接表示空安全状态，不创建独立 unconfined 对象，也不分配空容器。
实际 x86_64 内核调试类型信息显示 `Credentials_` 从 M1 的 112 字节增加到 128 字节， 每份 cred 固定增加 16 字节，包含状态槽与锁。
这不等于每个进程的总内存成本固定增加 16 字节， 因为线程及其他内核对象也可能持有凭据。

`test/host/lsm_cred_alloc.rs` 编译实际的通用状态实现，只替换模块注册表和错误类型。
分配探针验证空状态初始化、复制、未匹配 exec 准备、提交与释放新增 0 次堆分配， 并分别注入候选容器的两个分配失败，验证返回 ENOMEM 且保留父状态。
它不测量整个 fork/exec，不包含原有 cred 分配、路径构造及查询字符串的临时分配。

组件直接保存不可变 `Arc<Profile>`，通用 core 不解释 AppArmor 类型。
exec 在提交点之前准备完整候选；
在原有 VMAR 锁保护下、可失败的凭据更新之后发布。
procfs 在同一 VMAR 锁下完成目标校验、授权及状态捕获，锁外格式化。

加载时只接受可证明为一个绝对 UTF-8 字面路径的 ABI v5 DFA；
拒绝通配、多路径、 不支持的压缩编码及不明确的接受语义。
保存派生路径并构建有序索引，不在 exec 中执行原始 DFA。
不同 profile 使用同一 attachment 会使整个加载以 EEXIST 失败。
计费包含原始输入大小、 派生路径和索引，属于保守上限，可能大于实际持有的 DFA 存储。

本次同时补上 M1 已实现能力的 `features/policy/set_load` 声明。
缺少此声明时， libapparmor 会把一份多 profile 二进制拆成对同一 `.load` 的多次写入，后续写入因非零 offset 返回 ESPIPE。
声明后 parser 使用已有的整批原子加载路径；
没有放宽 `.load` 的 offset 规则。

## 审阅与边界

独立审阅固定范围为 `0c527109..7712b02`，追踪了 exec 提交时机、实际 fork/clone 调用点、 PID/TID 身份和授权、路径重解析、DFA 验证与重复 attachment 的原子拒绝，未发现确定的 Critical/Important 语义缺陷。
两条收尾意见是提交文本的 CRLF 和 literal 计费的直接回归覆盖。
两个文件已规范为 LF；
计费测试使用真实 parser fixture，覆盖准确计费、刚好达到上限、 超限一字节拒绝及旧快照不变。
临时漏算变体先失败，恢复实现后 27 项 AppArmor 单测通过。
恢复时发现启动包装器仍跟踪上一 crate 的 payload，已触发其重新构建后验证；
陈旧镜像的 失败记录没有计入正常实现的测试结果。

以下设计取舍保留：

- 复用 `LsmModule` 的默认方法，组件直接持有 `Arc<Profile>`；
  没有单独的 label 容器。
  将来若引入标签叠加，需要扩展当前表示和查询选择方式。
- 加载时证明唯一字面路径并丢弃原始 DFA。
  exec 的查找简单且有界，但会拒绝本阶段未支持的 DFA 编码及部分语义等价的非规范表达，保守计费也可能更早达到存储上限。
- 分配探针使用实际通用状态代码及测试注册表，不替代内核分配器集成故障注入。
- PID 查询捕获入口所指的对象；
  现有全局 PID 分配器没有正常复用路径，本次没有声称实测 PID 复用。
- 权限执行、profile 转换、替换/删除及标签叠加仍在后续阶段。
  已有标签跨 exec 保留，不等于 已经实施 AppArmor 的 `ix` 规则。
